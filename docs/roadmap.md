# Roadmap: the two-weekend test, run by machines

## The bet

The blind-battle arena only works where the product *is* the output: voice, transcription,
image, video, translation. In those categories buyers search "X vs Y" and get feature tables
from G2-style directories. We give them the actual outputs on a fixed public prompt set,
scored the same way for every tool, and a vendor-verified listing plus an embeddable badge
that vendors want because it is proof rather than a paid review.

The company is a loop: **execute → score → publish → measure**, with the arena UI from the
original brief as the proof generator, not the product.

## Success test (decided before building)

One category (voice), five tools, thirty golden prompts, ten "X vs Y" pages.

Continue after 60 days if **both** hold:

- at least two of the five vendors have supplied an API key in response to outreach;
- the pages have received any organic search clicks.

Otherwise stop. The kill decision is made by a job, not a person (see Phase 4).

## Phases

### Phase 1 — Publisher (this branch)

- [x] Voice catalog: category metrics, five tools, thirty golden prompts (`data/catalog/voice/`).
- [x] Snapshot contract between pipeline and site (`apps/site/src/lib/snapshot.ts`).
- [x] Static site: home, category leaderboard + prompt bank, ten comparison pages, five tool pages, methodology, sitemap. Real tools render in a visible "benchmark pending" state; scores are never estimated.
- [x] Fictional demo dataset for previewing the populated layout (`SNAPSHOT=demo`), with `noindex` and a banner.
- [x] GitHub Pages deploy workflow.
- [ ] Domain + `SITE_URL`/`PUBLIC_CONTACT_EMAIL` set in the workflow (human: buy domain, create mailbox).

### Phase 2 — Runner and scorer

- [x] Minimal runner (`scripts/run-voice.mjs`) with an Inworld adapter: streams audio, records TTFB and total latency, idempotent, publishes failures. Tested against a local mock; first real run needs egress to `api.inworld.ai` (blocked in the current Claude Code environment's network policy).
- [x] Exporter merges `data/runs/` into the snapshot; site renders outputs with the scorecard pending.
- [x] Adapters for OpenAI, ElevenLabs, Cartesia (untested live). Google and Polly still need signed-auth adapters.
- [x] `benchmark.yml`: runs on GitHub-hosted runners from repository secrets, commits runs, scores, redeploys. Weekly schedule.
- [x] Scorer (`scripts/score-voice.mjs`): Whisper transcript → WER → accuracy; LLM judge → adherence; naturalness left null until a MOS predictor backend exists.
- [x] Exporter computes velocity as a cross-tool rank per prompt, aggregates ratings and ranks, and writes a templated verdict per pair.
- [x] Embeddable SVG badge per tool at `/badge/<category>/<tool>.svg`, with the embed snippet on the tool page.
- [ ] Naturalness backend (UTMOS/NISQA in a Python step on the runner).
- [ ] Multi-judge jury (the original five-model spec); today a single judge model, averaged later.
- [ ] Postgres. The catalog + `data/runs/` + snapshot in git is the system of record until there is interactive traffic (the arena UI); the schema in `db/` is kept for that phase.

- Generalise `jury_evaluations` from four fixed text columns to `scores jsonb` keyed by
  `categories.metrics`, so audio metrics (accuracy, naturalness, adherence, velocity) fit the
  same table. Amend `leaderboard_jury_scores` and the smoke test accordingly.
- Seed `categories`, `tools`, `prompts` from `data/catalog/` (one script, idempotent on slug/hash).
- Runner (TypeScript worker, `arena_proxy` role): for each (tool × prompt) without a canonical
  execution, call the adapter, store audio in object storage, write `executions` with TTFB and
  latency. Cost cap per run; retries on transient errors; stops the tool after 5 consecutive failures.
- Scorer, per modality. Voice: ASR transcript → word error rate → accuracy; UTMOS/NISQA →
  naturalness; LLM jury over transcript + constraints → adherence; latency percentiles → velocity.
- Exporter: `scripts/export-snapshot.mjs` reads Postgres when `DATABASE_URL` is set and emits
  the same snapshot shape. The site does not change.
- Copy generation: verdict headline + summary per pair from the scores, generated by an LLM
  from a fixed template, regenerated on every export so it never drifts from the numbers.
- Scheduled workflow: weekly run → score → export → build → deploy.

Human touchpoints in this phase: create the vendor accounts and pay for the first keys, and
allow the vendor API hosts in the environment's network policy (or run the runner locally).
Keys live in `.env` only. A key pasted into a chat should be rotated after the run.

### Phase 3 — Vendor loop

- Claim form that accepts a key into `vendor_api_keys` (encrypted at write, validated with one
  golden prompt, status flips to `active` and the tool to `vendor_verified`).
- Outreach agent: one email per vendor from the project mailbox, pointing at their live page and
  the claim form; one follow-up after 14 days; replies triaged by an agent, escalation to a human
  only for legal or commercial questions.
- Embeddable badge: `/badge/{category}/{tool}.svg` rendered from the snapshot at build time,
  with the composite score and rank; links back to the tool page.

### Phase 4 — Measure and decide

- Search Console API → clicks per page per day into `data/metrics/clicks.json`.
- [x] `scripts/verdict.mjs` evaluates the success test from `data/metrics/clicks.json` and the
  vendor-key state in the catalog, and prints CONTINUE or STOP with the numbers. The day-60
  workflow will run it and open an issue with the output. That issue is the decision.

## What stays human

Company registration, bank and payment accounts, domain purchase, accepting each vendor's
API terms, and the first round of API spend. Everything after that runs on schedule.
